# 代码库解读

给想用、想学这个项目的人写：读完知道它是什么、解决什么麻烦、自己能不能跑起来、有什么坑。第一人称实测，口语但准确。用户当次的要求优先。

## 先读、先跑，再写

- README 当作者自述看：写进稿子的每个功能都要在代码、示例或文档里找到；「快速开始」照着做一遍。
- 版本和日期看 Releases 或 CHANGELOG；维护状态看最后一次提交、贡献者数、是否归档；去 Issues / Discussions 看已知 bug、维护者多久回复、有没有安全公告。
- 许可证要写清楚：没有 LICENSE 等于保留所有权利，别人只能看和 fork；分清真正的开源和「源码可见」（非商用许可、BSL 这类）；模型权重常另有许可。
- star 数只作参考，写明截至哪天：假 star 很常见（研究估计有数百万），尤其 AI、区块链、工具类项目；曲线突然陡升要警惕。
- 认准官方仓库，不把 fork 或仿冒当原项目；项目自己公布的跑分写「官方称」。
- 在干净环境里亲手跑一遍，记下系统、版本、耗时和报错。没跑过不写「实测」。

## 结构（6–8 张）

1. 封面：项目名 + 一句话说清它替你做什么（讲场景，不讲参数），小字写 owner/repo（用小标签）。
2. 痛点：以前怎么做、哪里麻烦；适合谁，也写不适合谁。
3. 它是什么：一句定义、三个核心能力、比同类强在哪（标签列表）。
4. 原理：用白话讲数据流「输入 → 处理 → 输出」；源码导读型改成「目录地图 → 主流程 → 一个值得学的设计（不超过 10 行代码）」。
5. 上手：前置条件（系统、硬件、API Key 与费用、网络）；不超过 3 步的命令放等宽块；实测耗时和踩过的坑。
6. 局限：已知问题、维护状态、数据会不会上传、许可证限制。
7. 信息卡：许可证、语言、最新版本与日期、star 数（截至哪天）、一句结论；最后抛一个具体问题引评论。

## 标题与正文

- 标题不超过 20 字，关键词放前面：「X：一句话用途」「实测 X，适合谁不适合谁」「N 个 XX 开源工具」。不用「吊打 / 封神 / 全网最强 / 白嫖」。
- 小红书正文：一句话介绍 → 适合谁 → 关键事实 → 只写 owner/repo 让人自己去搜 → 实测环境。话题 3–5 个：一个大词（#GitHub #开源项目 #程序员）、两个精准词（#AI工具 #效率工具 #独立开发）、一个语言或领域词。
- 讲自己为什么用、解决了什么具体需求，比罗列功能更有人看；别用和内容不搭的生活化标题吸引错的人。

## 语气

- 术语第一次出现时用一句白话或类比解释；项目名、命令、API 名保留英文。
- 代码只放安装和运行命令，效果用截图；不整屏贴代码。
- emoji 只当分节符，每张不超过两个。

## 不要做

- 把 README 翻译一遍就当解读；用 star 数证明好用；随便叫「平替」。
- 漏写许可证、费用、网络前提；数字不带日期。
- 推荐破解、绕过付费、爬取个人信息的项目，或教绕过网络限制。
- 不写「私信领取」「评论扣 1」，截图去掉其他网站的水印和 logo（小红书管站外导流）。
- 用过 AI 的内容发布时勾选 AI 声明，人看过再发。
